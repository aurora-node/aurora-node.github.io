The quest of OAuth2


But what about Learning?

You stumble upon opaque and non-opaque tokens, introspection end-points, grant types and you ask yourself what in the world is OAuth2 and all of these new words. How does it all fit together? You think to yourself, "I should Google and find a good resource to learn". Right? Welp. Probably not.

Most, if not all introductions on how to code something along the lines of OAuth2 with Spring are mediocre at best. No name third-party libraries cluttering your project, an abundance of outdated videos in every corner of the internet, and weird approaches on how to learn application security to finally reach your goal of building something with OAuth2.

Lots of bookmarks later and skimming through web pages I concluded that it is best to create something from scratch and by "from scratch" I mean: learning the underlying theory, working with what Spring offers directly, and building an OAuth2 flow from the ground up without relying too much on something that solves the problem for you, such as an authorization server that sets up token creation and authentication for you out of the box. It is better to try and do something on your own, at least for the first time.

Prototyping, Tracer Bullets, and how the two relate together

Before diving into OAuth2 and Spring, I would really like to include in this post a handful of quotes from a greatly written book called The Pragmatic Programmer by David Thomas and Andrew Hunt. They convey an interesting approach on how to think and act when programming. It is an amazing book to open and read through and lots of points hit home hard.

I remember reading the "Listen to Your Lizard Brain" and "Fear of the Blank Page" topics and laughing to myself. Have you ever had a brief unsettling feeling but you couldn't pinpoint what it is when you program? That's your instinct and lizard brain telling you something that hasn't surfaced yet!

Or have you ever found the initial blank page a bit daunting? Maybe it is time for some disposable code and a prototyping session!

A good way to overcome coding doubts is to take action. Prototypes are meant to be thrown away and a good way to experiment without pressure or the expectation to write something that will stick. It is ephemeral code. You write it and say your goodbyes.

Remember that when we prototype something as we said, we throw it away in the end. This is especially useful as from prototyping we might learn something new, take the lessons learnt and mold them into something better later on.

Crossing at the other side of prototyping, lets see what tracer bullets are and how they relate to prototyping. Here is a quote that frames prototyping and tracer bullets together.

But what is a tracer bullet and how does it even relate to programming? Tracer bullets leave a distinct trail behind them and help a soldier hit their target. Now if we try and find the analogy in programming on what tracer bullets are, simply put they are the process you go through from taking an initial requirement to reaching a complete sub-part of the final system you are trying to build, an end to end connection with all the components you have for the system to work. Tracer code is lean and forms the initial scaffold of the project.

Coffee Beans: Spring Authorization and Resource Servers

Continuing with Spring, the sketch below really helps to visualize the big picture of what's going on with the two servers. Starting on the right-hand side we got the coffee bean tree (Authorization Server) that grows the coffee beans (Tokens). It can be configured to our liking and mint lots of tokens. Even different kinds of tokens which is called multi-tenancy! You could mint both opaque and non-opaque tokens.

On the left-hand side we have something else; a sack of beans that fetches tokens which were issued by the coffee bean tree. The sack figures out if they're legitimate by asking the tree and by examining the token, it knows which parts of the software can be reached by applying authorization rules.

The thing I liked the most though, is how the traveling of the coffee beans (tokens) takes place. At first you augment them in the authorization side however you find fit, and mold information to travel into a list since you can add a list of authorities into the token. On the flip side, you do the opposite; you take the list from the token, unmold it into authorities and feed the bean sack with the authorities. This way the user can access only what you want them to.

There are a lot of details omitted in this overview such as the ordering of filters, how the keys are generated or how the resource server communicates with the other side but I'd like to keep it short and focus on the big picture of the two servers.

For details not being omitted a good book is Spring Security in Action by Laur Spilca which inspired me to sketch with coffee beans. It also explains OAuth2 in great detail; from theory to basics, and implementations. No weird-third party libraries and bad approaches. Paired with official Spring documentation learning OAuth2 becomes a walk in the park.



A small detour in the world of Self-Hosting

A small detour worth taking. There's a running joke online where the Raspberry Pi always ends up on a shelf and having the fate of being permanently dusted. My Pi has had that fate in the past, a couple of times but it was high time to give it some proper meaning and that's where self-hosting came into play. Mind you, that the following setup works closely with Tailscale that lets me have an "overlay-network" as they state so I can access my devices everywhere I go securely.

The project I was creating involved OAuth2 for a React Client, but I also wanted to include code versioning and some kind of CI/CD to automatically test my code and push Docker images.

This was the perfect case of reviving the Raspberry Pi so I decided to self-host a free and open-source alternative to GitHub called Gitea. A few exciting parts of Gitea was, that it offered a local image registry and support to seamlessly integrate with a CI/CD engine called Woodpecker.

So it made sense to create pipelines in order to build the applications, test the software, and finally push images to both the local image registry in Gitea but also DockerHub to get over the whole fiasco of: "But it works on my computer!".

REST APIs Design

As for creating the REST APIs, I mostly did what I already knew except a couple of things. I properly used Spring Aspects to intercept exceptions with a RestControllerAdvice so I could keep the controllers lightweight and only introduced exceptions in the service layer. So when something went sideways the flow continued in the advice. 


    @RestControllerAdvice
    public class ExceptionControllerAdvice {
      // ...
      @ExceptionHandler(CreateTaskException.class)
        // ...
      }
      // ...
    }

Other than that, I modeled the requests, responses, error details, and used a mapper as an intermediary for actions such as: mapping to an entity or mapping to a response.

IntelliJ IDEA is helpful enough and provides a Bean Graph so we can see how all of the REST API beans relate to each other. The classes that model the request, the response and the errors are obviously omitted as they're not picked up by the Spring Container as a bean to augment them.



Testcontainers!

Woodpecker is interesting but what about testing our software? I found about Testcontainers in a video by Dan Vega a while ago. It was great all around and if you want to look into this kind of integration testing, in the end I have a handy link for the video along with some MySQL documentation from their official website.

I experimented with it and decided to include it in the project. They're essentially ephemeral containers that spin up when you do integration testing so you can have a real MySQL database to perform testing with. Woodpecker runs its steps in containers and also uses MySQL containers for the testing phase.

Testcontainers and JWTs

In the following snippet we can see the initial code needed to start working with Testcontainers. We use testing application properties rather than the normal ones. This is done so we can tell Hibernate to automatically create and drop the tables; @ActiveProfiles("test").

With @DynamicPropertySource instead of writing the datasource properties into the application properties file, we provide them from the container that spins up for testing since the datasource information is not known beforehand.

Also, the JwtDecoder is mocked out so we can later on adjust it. If we do not do this we won't be able to test the API. It needs the token attached as a Bearer {token-value} in the request. 


    // Full App Ctx with Test App Properties.
    @ActiveProfiles("test")
    @SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
    class TaskControllerTest {

      @LocalServerPort
      private int port;

      // One (1) container for many tests.
      static MySQLContainer mysql = new MySQLContainer("mysql:8.0.36");

      @BeforeAll
      static void beforeAll() {
          mysql.start();
      }
      @AfterAll
      static void afterAll() {
          mysql.stop();
      }

      // Instead of app properties, do this:
      @DynamicPropertySource
      static void dynamicProperties(DynamicPropertyRegistry registry) {
          registry.add("spring.datasource.url", mysql::getJdbcUrl);
          registry.add("spring.datasource.username", mysql::getUsername);
          registry.add("spring.datasource.password", mysql::getPassword);
      }

      @Autowired
      TaskRepository taskRepository;

      // Mock the JWT Converter
      @MockitoBean
      JwtDecoder jwtDecoder;

Before each method that is annotated with @Test we have the setUp(). Here we specify the base URI, we delete any leftovers in the database and in our case, create a simple Jwt. Note that by default in testing, the token is hard coded with a claim of "authorities" which contains a single authority of type "USER". This means that it will be authorized for end-points that permit this specific authority. 



    @BeforeEach
    void setUp() {

      RestAssured.baseURI = "http://localhost:" + port;

      // Needed since if we start another test old data must be purged.
      taskRepository.deleteAll();

      // Default token has `USER` claim so requests are authorized with this token.
      Jwt jwt = Jwt
              .withTokenValue("testing-token")
              // Not signed.
              .header("alg", "none")
              // `testing-user` will live in the database in the `userSub` column.
              .claim("sub", "testing-user")
              // `USER` authority claim.
              .claim("authorities", List.of("USER"))
              .build();

      // Stubbing method, when `decode` is called return the `jwt` above.
      when(jwtDecoder.decode(anyString())).thenReturn(jwt);
    }

Here is a simple test that instead creates a new Jwt and does not use the initial one from the setUp() method we previously saw. I created a new token with an authority that will be rejected by the Resource Server. As such, we expect the response to be a 403 forbidden status code when we try and hit the /api/v1/tasks end-point. 


    @Test
    void fetchAllTasks_withInvalidTokenAuthority_returns403() {

        Jwt jwt = Jwt
                .withTokenValue("testing-token")
                .header("alg", "none")
                .claim("sub", "testing-user")
                // Jwt with `NOT_USER` Claim.
                .claim("authorities", List.of("NOT_USER"))
                .build();

        // Instead of initial `jwt` we get the above one.
        when(jwtDecoder.decode(anyString())).thenReturn(jwt);

        given()
                .header("Authorization", "Bearer testing-token")

                .when().get("/api/v1/tasks")

                .then()
                    .statusCode(403);
    }
